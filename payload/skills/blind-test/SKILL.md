# blind-test — 让测试真的能证伪

写测试的人和写实现的人共享同一个上下文时,测试会退化成「把实现抄一遍」。
模型在同一个 latent space 里,统计上就倾向于生成**能验证自己错误**的测试:
实现里把 `<=` 写成 `<`,测试的边界值也跟着挑那个不会暴露差异的。

这不是态度问题,是结构问题。**换顺序解决不了,必须换人。**

实证:agent 自写测试时,「解决了的任务」与「没解决的任务」写测试的频率没有差别——
测试根本不具备区分能力;而且这些测试多数充当观察用的打印语句,而非断言检查。

## 完成合同

一次 blind-test 只有下面四项都有明确结果才算完成:

| 项 | 要回答的问题 | 证据 |
|---|---|---|
| 契约 | 被测的是什么行为?边界在哪? | 里程碑验收条款清单,不含实现细节 |
| 隔离 | 测试作者看过实现吗? | 独立上下文/子 agent + 工具权限;降级模式需说明 |
| 经济 | 每个测试都换来了什么? | 每条测试 ↔ 一条验收条款,一一对应 |
| 证伪力 | 这些测试真能挂吗? | 变异检查:注入的每个变异都至少挂一个测试 |

任一项做不到就如实标 `pending`,**不要用「测试全绿」冒充「测试有效」**。
全绿只证明当前实现与当前断言自洽,不证明断言有意义。

## 三个角色与防火墙

```
        契约(里程碑验收条款)
                │
    ┌───────────┴───────────┐
    │                       │
测试作者                 实现者
读得到:契约              读得到:失败的测试 + 契约
读不到:实现              读不到:测试作者的推理过程
写得了:测试文件          写得了:实现文件
写不了:实现文件          写不了:测试文件
```

**关键在工具权限,不在提示词。** 只靠「请你不要看实现」约束不住——把权限收掉才有效:
测试作者没有编辑实现的权限,就无法把实现改成配合测试;实现者拿不到测试作者的推理,
就只能从断言反推意图。

平台落地方式(以当前环境实际支持的为准,不确定就探测):

- **Claude Code**:用 Agent 工具派子 agent,在 `.claude/agents/*.md` frontmatter 里限定
  `tools`;或用 skill frontmatter 的 `allowed-tools`(实验字段,支持度按平台文档核实)。
- **其他平台**:找该平台的子 agent / 受限工具机制;找不到就走下面的降级模式,
  并在汇报里明说隔离是靠约定而非强制。

**降级模式(单会话、无法派子 agent)**:退而求其次,但必须做满这三条,否则不算隔离——

1. 先写契约与测试**代码**,`git commit` 落盘;
2. 提交后才开始实现,实现期间**不修改测试文件**;真要改,先说明理由并单独提交;
3. 收尾必须做变异检查——降级模式下它是唯一还能证明测试有效的手段。

## 里程碑 → 验收条款 → 测试,一一对应

这是控制冗余的唯一规则:**没有验收条款就没有测试,一条验收条款最多一个测试。**

先把里程碑写成可判定的验收条款。条款要能被一句话判真假,不含实现细节:

```text
M1 标记块 upsert
  A1  文件无标记时,块追加到末尾,原内容一字不改
  A2  文件已有配对标记时,块被替换,块外内容一字不改
  A3  标记孤立或逆序时,拒绝改写并返回 unpaired,原文原样返回
  A4  CRLF 文件写回后仍是 CRLF,不混入孤立 LF
```

四条条款 → 四个测试。**不多写第五个。**

条款怎么挑:只写「错了会让用户受损」的行为——数据被吞、边界算错、失败被当成成功、
契约对外承诺过的东西。「函数能被调用」「返回值不是 undefined」不是验收条款。

## 测试经济学:什么不配有测试

删掉或根本不要写下面这些。它们是 agent 写测试时的默认产物,占了体积却不提供证伪力:

| 反模式 | 为什么没用 |
|---|---|
| 测框架/库本身的行为 | 你在测别人的代码;它坏了不是你的测试该发现的 |
| 测 mock 的行为 | 断言只证明 mock 存在,与真实行为无关 |
| 一个函数一个测试 | 函数不是行为单位,验收条款才是;私有函数尤其不该有测试 |
| 把实现语句反过来抄成断言 | 实现改一行测试就挂,但从没发现过 bug——这是耦合,不是覆盖 |
| 同一条款的多个近似用例 | 输入 1、输入 2、输入 3 都走同一分支时,只留一个 |
| 快照/golden 文件当主要断言 | 它锁的是当前输出,不是正确性;实现错了照样能"通过"更新快照 |
| 只断言"没有抛异常" | 不抛异常和行为正确是两回事 |

**判据**:说不出「这个测试挂掉时,用户会遇到什么问题」,就删掉它。

## 变异检查:唯一的机械证明

前面几条都是流程约束,靠人守。变异检查是唯一能**自动**证明测试有效的手段,必须做。

做法(不需要装任何变异测试框架):

1. 确认工作区干净(`git status`),否则先提交或 stash——**变异必须能被完整还原**。
2. 针对本里程碑的核心逻辑,挑 **3–5 处**注入变异,每次只改一处:
   - 边界:`<=` → `<`、`>` → `>=`
   - 条件取反:`if (x)` → `if (!x)`
   - 删守卫:去掉一个提前 return / 校验分支
   - 换返回值:成功码换失败码、返回 `null` 换返回空对象
   - 改常量:阈值 ±1
3. 每注入一处就跑测试。**必须至少有一个测试挂掉。**
4. `git checkout -- <文件>` 还原,再做下一处。全部做完后确认工作区回到干净。

**存活的变异 = 假测试。** 说明这条行为其实没被任何断言覆盖。两种处理,必须二选一,
不许含糊过去:

- 这条行为重要 → 它对应哪条验收条款?补上那个测试;
- 这条行为不重要 → 在汇报里明说「该分支不做验证」,不要假装它被测了。

变异检查的成本与做法细节(选哪些位置、各语言的最小操作)见
[references/mutation-check.md](references/mutation-check.md)。

## 最终自检

- [ ] 每条测试都能指回一条里程碑验收条款;没有孤儿测试。
- [ ] 每条验收条款都有且只有一个测试;没有近似重复用例。
- [ ] 测试作者与实现者的隔离方式已写明;降级模式已如实说明是约定而非强制。
- [ ] 降级模式下,测试代码在实现之前已单独提交。
- [ ] 变异检查已执行,注入位置与结果已记录;存活变异已给出处置(补测试 或 明示不验证)。
- [ ] 工作区已还原,没有遗留任何注入的变异。
- [ ] 没有把「测试全绿」当成「测试有效」来汇报。
- [ ] 反模式表逐条对照过,没有测框架、测 mock、抄实现的用例。

## 汇报

```text
## blind-test 完成

**里程碑**:<M1 名称>

| 条款 | 测试 | 变异检查 |
|---|---|---|
| A1 <一句话> | <测试名> | 注入边界变异 → 挂 ✓ |
| A2 <一句话> | <测试名> | 注入条件取反 → 挂 ✓ |
| A3 <一句话> | <测试名> | **存活** ← 见下 |

**隔离方式**:<子 agent + 受限工具 / 降级模式(测试先提交,commit <hash>)>

**存活变异**:<注入了什么、为什么没挂、补了测试还是明示不验证>

**未验证的行为**:<明确列出;没有就写「无」>
```

不要在这份汇报里写「测试全部通过」——那是运行结果,不是结论。
结论是「哪些行为被真正验证了,哪些没有」。
