# 变异检查实操

目的:证明测试**能挂**。存活的变异说明那条行为没被任何断言真正覆盖。

不需要安装 mutmut / Stryker / PIT 之类的框架。手工注入 3–5 处就够——
框架的价值是穷举,而这里要的是**抽样证伪**,穷举反而慢且噪音大。

## 挑哪些位置

按「改坏了用户会受损」排序,只动本里程碑涉及的代码:

| 优先级 | 位置 | 理由 |
|---|---|---|
| 高 | 边界比较、循环终止条件 | off-by-one 是最常见且最难靠肉眼发现的缺陷 |
| 高 | 提前 return / 守卫分支 | 删掉它通常不影响 happy path,只有真正测了异常路径的测试会挂 |
| 高 | 错误处理与返回码 | 「失败被当成成功」是最贵的一类 bug |
| 中 | 常量、阈值、默认值 | 容易被硬编码进断言,反而测不出 |
| 低 | 日志、格式化字符串 | 除非它就是对外契约,否则不值得占用配额 |

**不要变异**:第三方库调用、纯类型声明、注释。改了也证明不了自己的测试。

## 五种变异算子

一次只改一处,改完立刻跑测试,跑完立刻还原。

```
边界      <=  →  <        >  →  >=        ==  →  !=
条件取反  if (x)  →  if (!x)
删守卫    去掉一个提前 return / throw / 校验分支
换返回    成功 → 失败、null → 空对象、true → false
改常量    阈值 ±1、超时 ×10、重试次数 → 0
```

## 流程

```bash
git status                      # 必须干净，否则先提交或 stash
# —— 注入第 1 处变异（手工编辑）——
npm test                        # 期望：至少一个测试挂掉
git checkout -- <被改的文件>     # 立即还原
# —— 重复 3–5 次 ——
git status                      # 必须回到干净
```

**还原是硬要求。** 变异残留在工作区里被提交出去,比没做变异检查更糟。
每次注入后立刻还原,不要攒着一起还原。

## 判读结果

| 现象 | 含义 | 处置 |
|---|---|---|
| 变异 → 测试挂 | 该行为被真正覆盖 | 记录,继续 |
| 变异 → 全绿 | **假测试**:该行为无人验证 | 补测试,或在汇报里明示「不验证」 |
| 变异 → 测试报错而非断言失败 | 覆盖存疑:可能只是撞崩了,没验证行为 | 当作存活处理,检查断言是否真在检查输出 |
| 变异后测试挂了一大片 | 变异点太核心,信息量低 | 换个更局部的位置重做 |

最后一行值得展开:如果改一个常量导致 20 个测试全挂,这**不能**说明测试有效——
只说明它们都耦合在同一条路径上。真正有价值的信号是「挂了 1 个,且正是对应那条验收条款的那个」。

## 成本控制

- 每个里程碑 3–5 处,不是每个函数 3–5 处。
- 单次检查的总耗时应当接近「跑 3–5 遍测试」,超出说明选点太散。
- 同一处代码在后续里程碑不必重复变异,除非它被改动过。
- CI 里**不要**跑变异检查——它需要改工作区,属于开发期动作;
  要在 CI 固化,就把发现的缺口补成普通测试。
