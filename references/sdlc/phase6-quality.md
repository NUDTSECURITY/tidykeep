# 阶段 6：质量验证

**角色**：测试工程师
**目标**：上线前综合质量验证，包含静态分析、测试用例设计与动态执行验证

## 触发条件

- 所有模块开发完成并通过对齐检查

## 验证范围（必须全部覆盖）

---

### 6.1 功能符合度验证

对比 PRD 需求 vs 实际实现：
- 功能偏差：需求预期 vs 实际行为，偏差说明与影响
- 功能缺失：需求中存在但未实现的内容
- 功能冗余：实现中存在但需求未要求的内容

---

### 6.2 功能联动验证

- 多步骤流程是否闭环
- 模块之间是否正确调用
- 数据是否正确传递
- 是否存在功能孤岛

---

### 6.3 用户流程验证

- 模拟用户核心路径，逐步验证是否可走通
- 识别流程断点

---

### 6.4 代码质量检查

- 空值/None 处理
- 异常处理与错误提示
- 参数校验
- 逻辑漏洞
- 明显性能问题

---

### 6.5 边界与异常验证

- 空输入、非法输入、极端值
- 重复操作、快速连续操作
- 并发场景（如适用）

---

### 6.6 隐性需求风险识别

基于经验识别需求中可能缺失但实际必须存在的能力：
- 权限控制缺失
- 数据限制缺失
- 异常提示缺失
- 安全漏洞风险

---

### 6.7 状态一致性与数据流检查

- 操作结果是否真实生效（是否存在"假成功"）
- 输入 → 处理 → 输出 是否一致
- 数据是否存在丢失/错误/未使用

---

### 6.8 功能测试方案设计

**目标**：基于 PRD 设计可执行的功能测试用例，输出 POC 格式的测试方案

> **时序要求**：本节的**设计**工作必须在阶段 5 开发之前完成——由看过实现的人来出题，
> 测试会退化成把实现抄一遍，永远测不出问题。契约先行、测试作者与实现者上下文隔离、
> 里程碑验收条款与测试一一对应、变异检查证明测试能挂，这些由 `blind-test` skill 定义，
> 同装时以它为准。本节只保留 POC 文档的产出格式与采纳流程。

**执行规则**：
- 按 PRD 的功能模块，为每个功能点设计测试用例
- 每个测试用例必须包含：
  - 测试项编号（如 T01、T02）
  - 测试名称
  - 预置条件（环境、数据、权限准备）
  - 测试步骤（编号列表，具体到操作）
  - 预期结果（每个步骤对应的期望输出）
- 区分测试类型：Web UI 测试、API 测试、CLI 测试、单元测试
- 识别哪些测试用例可以通过当前环境的工具执行（浏览器、HTTP、命令行）

**输出格式**：
- 生成 POC 格式功能测试方案文档（Markdown / docx）
- 包含：测试方案概述、测试项清单总览、各模块详细测试用例

**约束**：
- 禁止一次性输出全部测试用例，按模块分批输出
- 每个模块的测试用例输出后必须询问：是否采纳

---

### 6.9 动态功能验证

**目标**：实际运行系统，执行测试用例，验证功能是否符合预期

**执行方式**（根据项目类型选择）：

**Web 应用**：
- 启动开发服务器或访问已部署的系统
- 使用浏览器工具访问页面，按测试步骤操作
- 关键步骤截图记录
- 对比实际页面状态/输出 vs 预期结果

**API 服务**：
- 使用 HTTP 请求工具发送请求
- 验证响应状态码、响应体结构、数据正确性
- 测试边界输入（空值、非法值、超长值）

**CLI 工具**：
- 执行命令行操作
- 验证输出内容、退出码、副作用（文件生成等）

**执行规则**：
- 按 6.8 设计的测试用例逐一执行
- 记录每个测试用例的实际结果：通过 / 失败 / 阻塞
- 对失败的用例，分析失败原因（环境问题、实现缺陷、用例设计问题）
- 阻塞的用例需说明原因（环境不可用、依赖缺失等）

**必须询问**：
- 动态验证结果是否采纳
- 失败的测试用例是否需要进入修复阶段

---

## 验证报告模板

**必须输出结构化验证报告**（综合静态验证 + 动态验证）：

```
【综合结论】
- 功能符合度：完全符合 / 部分符合 / 不符合
- 代码质量：高 / 中 / 低
- 动态测试通过率：X / Y（通过数 / 总数）
- 是否建议交付：是 / 否
- 核心问题数量：X 个

【问题清单】（按严重程度排序）
- 🔴 高风险问题（必须修复）：...
- 🟡 中风险问题（建议修复）：...
- 🟢 低风险问题（可选优化）：...

【动态功能测试结果】
| 测试项 | 类型 | 结果 | 备注 |
|---|---|---|---|
| T01 | Web UI | 通过 | ... |
| T02 | API | 失败 | ... |

【快速验证建议】
- 3~5 条人工验证建议
```

---

## 行为约束

- 不允许只做代码审查，必须验证功能（包括静态分析和动态执行）
- 不允许跳过动态功能验证（若环境允许）
- 不允许说"看起来没问题"
- 必须指出具体问题并给出修复建议
- 动态测试失败时，必须区分是环境问题还是实现缺陷
